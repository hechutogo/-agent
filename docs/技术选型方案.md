# 技术选型方案：Mac XLeRobot RGB-D Agent

> 本文对应当前已部署代码，不描述根目录保留的旧 Panda PoC。

## 1. 目标与硬约束

项目目标是在 Apple Silicon Mac 上提供可直接运行的 ManiSkill 3 仿真：

- XLeRobot 轮式双臂机器人形态；
- 当前锁定底盘，右臂操作，左臂保持；
- 用户通过文字或语音选择零件 A/B；
- 机器人执行移动、抓取、抬起、放置、复位；
- 完成后主动询问“还需要什么？”；
- 无云端凭据时仍能运行完整的本地 RGB-D 物理演示。

硬约束：

1. Agent 和运动层只使用 RGB-D、相机标定和机器人本体状态。
2. 禁止使用物体真值 pose、接触、分割 ID、奖励或环境成功标志。
3. AI 模型通过云端 API 调用，不在本地部署模型权重。
4. 模型只选择语义目标，不生成坐标、关节角或低层控制量。
5. 失败不能被 LLM 文本包装成成功。
6. 项目必须有无 Key 的可运行自检和真实物理抓取证据。

## 2. 总体架构选型

当前采用分层架构：

```text
输入层       文字 / 云端 ASR
                |
Agent 层     Qwen-Agent + 受限 BaseTool
                |
感知层       云端 VLM bbox 或本地颜色定位
                |
几何层       实测深度 + 标定反投影
                |
技能层       固定五段 PickPlace
                |
运动层       URDF FK/IK + 关节目标跟踪
                |
身体层       ManiSkill 3 / SAPIEN / XLeRobot
```

这一架构复用现有 Agent 框架，但不把通用 Agent 误当成完整具身系统。
机器人、感知、运动、技能和安全状态都由本项目实现。

## 3. 仿真框架：ManiSkill 3

### 3.1 候选对比

| 维度 | ManiSkill 3（选用） | Isaac Sim / Isaac Lab | MuJoCo | RoboTwin 2.0 | 直接使用 SAPIEN |
|---|---|---|---|---|---|
| Mac 可运行性 | 已在 Apple Silicon 验证 | 主要依赖 NVIDIA/RTX | 较好 | 当前集成和资产改造成本高 | 可运行 |
| 物理与渲染 | SAPIEN/PhysX，RGB-D 完整 | 强，但部署重 | 接触稳定，需自己搭上层 | 偏基准与任务生态 | 与 ManiSkill 同底层 |
| 自定义机器人 | 可注册 `BaseAgent` 和 URDF | 支持，资产转换较重 | 支持，控制器需自建 | 更适合其预定义任务体系 | 全部上层需自建 |
| 控制器 | ManiSkill PD 控制器可复用 | 完整但复杂 | 需自建 | 依任务而定 | 需自建 |
| 环境 API | `BaseEnv`、相机、张量观测 | Isaac API | 原生 API | RoboTwin API | 无 ManiSkill 封装 |
| 当前项目成本 | 最低，已跑通 | 硬件和安装不匹配 | 迁移无直接收益 | 偏离本次 ManiSkill 目标 | 重复实现环境层 |

### 3.2 选择理由

- 用户明确要求使用 ManiSkill 3；
- SAPIEN 3 提供物理、相机和 URDF articulation；
- ManiSkill 的 `BaseEnv`、`BaseAgent`、`PDJointPosControllerConfig`
  能直接承载自定义 XLeRobot；
- RGB-D、相机标定和本体状态可通过统一观测接口输出；
- 已在 Apple M5 Pro 上完成真实渲染和物理抓取验证。

`sim_backend="cpu"` 和 `render_backend="cpu"` 是 ManiSkill 在 Mac 上的
兼容配置。实际图形设备通过 MoltenVK 使用 Apple GPU/Metal，因此不应宣传为
“纯 CPU 渲染”。

### 3.3 为什么不直接使用 RoboTwin

RoboTwin 是有价值的双臂任务与数据生态，但本项目当前要求是：

- 从指定 GitHub 项目演进；
- 使用 ManiSkill 3；
- 接入 XLeRobot 自定义模型；
- 严格限制为 RGB-D + 本体观测；
- 在 Mac 本机形成最小可运行闭环。

直接迁移 RoboTwin 会引入任务定义、资产和执行接口重构，不能自动解决当前
XLeRobot URDF、Mac 渲染、感知边界和夹爪控制问题。现阶段保留 ManiSkill 原生
实现更直接。以后需要 RoboTwin 数据集或双臂任务时，可在不改变非特权原则的
前提下单独评估迁移。

## 4. 机器人：XLeRobot

### 4.1 选择

采用 `Vector-Wangel/XLeRobot` 的仿真资产，固定 revision：

```text
a7ee564294f03484783ed053ab1550bccc3c6c09
```

选择理由：

- 形态满足轮式双臂目标；
- 提供可载入 SAPIEN/ManiSkill 的 URDF 和 mesh；
- 每臂 5 个运动关节，适合当前桌面抓放尺度；
- 可保留双臂和移动底盘的后续扩展路径。

### 4.2 当前部署边界

- 三个根部移动关节改为 `fixed`，并启用 `fix_root_link`；
- 仅右臂执行；
- 左臂、头部、左夹爪保持初始目标；
- 未实现底盘导航或双臂协同；
- 上游项目称为 v0.3 形态，但本项目未独立认证 URDF 与实体硬件的逐尺寸一致性。

这比继续使用旧 Panda 单臂更接近最终机器人形态，同时控制了第一阶段复杂度。

## 5. Agent 框架：Qwen-Agent

### 5.1 结论

当前选用 **Qwen-Agent 0.0.34** 作为通用 LLM Agent 编排框架，不自研
Assistant、消息历史或 function-calling 协议。

具身部分仍需项目实现：

- 目标授权；
- 动作预算；
- RGB-D 感知；
- IK；
- 物理技能；
- 视觉成功判定；
- 恢复锁。

因此不是“完全使用现成具身 Agent”，也不是“全部从零自研”，而是：

> 开源通用 Agent 框架 + 自研具身适配和安全执行层。

### 5.2 候选对比

| 方案 | 优点 | 当前问题 | 结论 |
|---|---|---|---|
| Qwen-Agent | Assistant/BaseTool 简单；OpenAI 兼容；现有仓库已使用 | 复杂状态机能力有限 | 当前选用 |
| LangGraph | 显式状态图、持久化、人在环路、恢复分支强 | 当前单工具流程引入成本偏高 | 复杂化后再迁移 |
| ROS 2 + BehaviorTree.CPP | 真机工程和行为树生态成熟 | Mac 仿真 PoC 部署重；与当前 Python 链路割裂 | 真机阶段候选 |
| 自研 Agent 循环 | 完全可控 | 重复实现消息协议、工具调度和历史 | 不选 |
| 多 Agent 框架 | 可拆角色 | 当前只有单机器人、单任务，增加不可控调用 | 不选 |

### 5.3 为什么不用完整现成“具身 Agent 框架”

不同机器人、相机、坐标系、控制器和任务成功条件差异很大。现成框架通常不能
直接提供“XLeRobot + 当前桌面 + 非特权 RGB-D + Mac ManiSkill”的即插即用技能。
强行接入更重框架仍然需要重写身体适配层，同时增加不可观察的规划行为。

当前更可靠的方式是保留 Qwen-Agent 负责语言和工具调用，把可验证的物理过程
封装成高层工具。这样既使用开源框架，也能保证执行边界。

### 5.4 迁移 LangGraph 的触发条件

满足任一条件时再迁移：

- 一个任务包含多个可选技能和条件分支；
- 需要可恢复的重新观察、重新规划；
- 需要人工批准关键动作；
- 需要跨进程 checkpoint；
- 需要任务队列和长期运行。

迁移时复用 `PickPlace.run()` 和感知接口，只替换 Agent 编排层。

## 6. 技能粒度：单一高层工具

### 6.1 当前选择

模型只看到：

```text
pick_and_place(target="A" | "B")
```

内部固定执行移动、抓取、抬起、放置、复位。

### 6.2 为什么不暴露五个工具

如果把 `move_to(x,y,z)`、`close_gripper()` 或关节动作暴露给模型：

- 模型可能生成错误坐标；
- 重复或乱序调用会改变物理状态；
- 难以定义每步的恢复条件；
- 无法证明一次用户命令只产生一次物理任务；
- 提示词错误可能直接变成危险动作。

单一高层工具把语言理解与确定性机器人控制隔离：

- LLM 决定“操作哪个零件”；
- 感知决定“零件在哪里”；
- IK 决定“关节怎么走”；
- 固定技能决定“动作顺序”；
- 视觉检查决定“是否成功”。

当新增独立语义任务时，可以增加新的高层工具，而不是开放底层控制。

## 7. 感知：云端 VLM + 本地 RGB-D

### 7.1 候选对比

| 方案 | 合规性 | 部署成本 | 泛化 | 当前用途 |
|---|---|---|---|---|
| 仿真 actor pose | 不合规 | 低 | 无 | 禁止 |
| 仿真分割 ID | 不合规 | 低 | 无 | 禁止 |
| OpenCV 颜色 + RGB-D | 合规 | 最低 | 仅当前颜色场景 | 本地确定性基线 |
| 云端 VLM bbox + 本地深度 | 合规 | 需要 API | 比颜色更灵活 | 云端 Agent 路径 |
| 本地 VLM/VLA | 不符合“不部署本地模型” | 算力和显存高 | 取决于模型 | 不选 |
| 云端直接输出 XYZ | 难校验尺度和坐标 | 中 | 不稳定 | 不选 |

### 7.2 当前选择

云端 VLM 只负责返回 RGB 像素 bbox 和置信度；三维几何在本地用实测深度、
相机内参和外参计算。

默认在 VLM bbox 内按当前已知颜色做局部细化。这是公开标注的场景先验：

- A：红色；
- B：蓝色；
- 盒子：绿色。

颜色细化不是本地 AI 模型，也不是仿真分割。它提升当前简单场景的几何稳定性，
但不代表已支持开放词汇或任意外观。

### 7.3 为什么保留本地颜色基线

- 无 Key 也能验证完整物理链路；
- 失败容易定位到视觉、深度、IK 或控制的具体层；
- 云端 VLM 结果可与确定性基线对照；
- 不把 API 可用性和机器人可运行性绑定。

本地基线必须明确标注为 OpenCV 演示，不能冒充云端 Agent 验收。

## 8. 运动规划：URDF FK/IK + 固定动作模板

### 8.1 当前实际实现

当前执行路径使用：

- XML 解析 XLeRobot URDF；
- SciPy `Rotation` 计算关节变换；
- SciPy `least_squares` 求 5-DOF IK；
- TCP 位置约束；
- 向下抓取接近轴约束；
- Wrist Roll 正则；
- 笛卡尔路点和关节 smoothstep 插值；
- 本体 qpos 和 FK 做跟踪检查。

`pin` 依赖虽然安装在环境中，但当前 `ArmKinematics` 不依赖 pinocchio。
旧文档中的 Panda pinocchio CLIK 不属于当前运行路径。

### 8.2 与其他方案比较

| 方案 | 优点 | 当前问题 | 结论 |
|---|---|---|---|
| 当前 SciPy 位置 IK | 跨 Mac；实现透明；5-DOF 约束可控 | 不含通用碰撞规划 | 当前选用 |
| mplib | IK、规划和碰撞能力完整 | Mac/自定义 XLeRobot 集成成本高；当前规则场景不必要 | 扩展障碍场景时评估 |
| MoveIt 2 | 真机和规划生态成熟 | ROS 2 栈较重；当前仿真链路成本高 | 真机阶段候选 |
| LLM 生成轨迹 | 表达灵活 | 不可验证且风险高 | 禁止 |
| 端到端 VLA | 可从视觉直接出动作 | 需模型、数据、训练和本地/远端推理链路 | 当前不选 |

### 8.3 为什么固定五段动作足够

当前场景只有桌面、两个小方块和一个固定盒子。统一从目标上方接近，
水平移动在抬升高度完成，可避免引入随机采样规划器。

固定原语的优势：

- 行为可复现；
- 每阶段可截图和检查；
- 失败位置明确；
- 可在动作开始前预检全部关键 IK；
- 适合当前验收，不增加无关复杂度。

若以后加入高障碍、动态障碍、移动底盘或双臂协同，应引入碰撞场景和正式规划器。

## 9. 控制器：绝对关节位置 PD

`PickPartsXLeRobot` 使用 ManiSkill `PDJointPosControllerConfig`：

- 右臂 5 关节；
- 左臂 5 关节；
- 头部 2 关节；
- 两个夹爪各 1 关节。

总动作向量按命名组拼接，当前只修改右臂和右夹爪，其他组保持之前目标。

选择绝对关节位置控制的理由：

- IK 输出可以直接下发；
- 目标明确、轨迹可复现；
- 可从 qpos 直接计算跟踪误差；
- 不需要模型维护增量积分状态。

夹爪力矩经过实际物理调试。过大闭合力会使轻量手臂失稳，因此当前使用
较低力矩和高摩擦接触参数。

## 10. 云模型与语音

### 10.1 LLM/VLM

所有模型使用 OpenAI 兼容云端接口，配置与代码解耦：

```text
LLM_API_KEY / BASE_URL / MODEL
VLM_API_KEY / BASE_URL / MODEL
ASR_API_KEY / BASE_URL / MODEL
```

默认示例为 DashScope Qwen 模型，但项目不绑定某一供应商。跨供应商配置时，
代码不会把一个域名的 API Key 自动转发到另一个域名。

### 10.2 ASR

音频通过云端 `/audio/transcriptions` 接口，不安装本地 Whisper。麦克风录音
使用可选 `sounddevice`，以 16 kHz 单声道 WAV 发送。

当前真实云端服务和麦克风没有完成验收，因此只能声明“接口已实现且单测通过”。

## 11. Mac 运行时

### 11.1 选择

- Python 3.11 独立 `.venv`；
- uv 负责环境和 pip 安装；
- ManiSkill 3.0.1；
- SAPIEN 3.0.3；
- 项目内 MoltenVK 1.4.2 和 libcxx；
- 不要求全局 conda 或系统 Vulkan SDK。

### 11.2 原因

SAPIEN 在本机没有找到系统 `libvulkan` 时使用自带 Vulkan loader，再通过
项目 `.runtime` 中的 MoltenVK 驱动 Apple GPU。项目内运行时可以：

- 避免修改系统环境；
- 固定版本；
- 对下载文件做 SHA-256 校验；
- 在损坏缓存或中断下载后重试；
- 保持安装可复现。

当前自动安装只支持 Apple Silicon。其他操作系统不能根据代码存在就声称已验证。

## 12. 测试与验收策略

| 层 | 测试内容 |
|---|---|
| 几何 | 深度反投影、无效深度、标定 |
| 指令 | A/B 解析、否定/歧义拒绝 |
| 云感知 | RGB 上传、bbox、置信度、深度、颜色细化 |
| Agent 工具 | 参数授权、每轮预算、重复调用、真实结果 |
| IK | 可达目标误差、不可达拒绝 |
| 仿真 | XLeRobot RGB-D、保持姿态 |
| 恢复 | 动作后失败锁定、诊断失败不解锁 |
| 安装 | 校验下载、原子替换、损坏缓存恢复 |
| 物理验收 | A 真实夹起、RGB-D 抬升、视觉入盒 |

实际记录：

- 123 项测试通过；
- A 抬升约 0.097 m；
- B 抬升约 0.091 m；
- 同一场景 A 后 B 成功；
- 默认窗口入口成功。

测试通过不能替代云端服务验收，也不等于多 seed 的统计成功率。

| Agent | Qwen-Agent 0.0.34 | 是 | 授权、预算、历史结果约束 | 复杂状态迁移 LangGraph |

## 14. 选型结论

当前方案没有重复造通用 Agent 框架，也没有依赖一个无法直接适配当前机器人的
重型具身框架。它把成熟开源组件用于其擅长的部分：

- Qwen-Agent 负责语言模型和工具调用；
- ManiSkill/SAPIEN 负责仿真和物理；
- XLeRobot 提供机器人资产；
- OpenCV/OpenAI SDK/SciPy 提供基础能力。

项目代码集中解决无法由通用框架替代的部分：

- 非特权观测边界；
- RGB-D 到机器人坐标的几何；
- 受限高层技能；
- 5-DOF IK 和物理执行；
- 视觉成功判定；
- 动作预算和异常恢复。

在当前固定桌面任务下，这是比“直接上完整 VLA/多 Agent/ROS 2”更可验证、
部署成本更低的方案。未来扩展应以任务复杂度为触发条件逐层替换，不应一次性
推翻已验证的传感器、技能和控制接口。
