# 技术选型方案：PickParts 具身智能 Demo

> 选型约束（来自实际条件）：**Windows 桌面、纯 CPU（torch CPU 版）、4GB 显存的旧机器、桌面固定 Panda 单臂**；目标是"方便后续优化、方便部署"，并为将来接真实机械臂和升级 VLA 小脑留好接口。
>
> 方法论参考 FAEA 范式（LLM agent 直接在 ManiSkill3 中完成感知-规划-行动闭环的已验证工作），整体按 **大脑（LLM/Agent 框架）— 技能接口 — 小脑（运动规划/策略）— 身体（仿真器/机器人）** 四层分别选型，层间只通过明确接口耦合。

---

## 1. 仿真框架：为什么选 ManiSkill3

### 1.1 候选对比

| 维度 | **ManiSkill 3.0.1（选用）** | Isaac Sim / Isaac Lab | MuJoCo / MJX | Genesis | PyBullet | 直接用 SAPIEN |
|---|---|---|---|---|---|---|
| 物理引擎 | SAPIEN(PhysX)，接触真实 | PhysX，真实 | 自研接触模型，抓握偏软 | 多引擎但生态新 | 老牌但接触表现一般 | 同 ManiSkill，但要自己造全部上层 |
| GPU 大规模并行 | 支持（本项目未用） | 最强 | MJX 强 | 强 | 弱 | 支持 |
| **CPU-only 可跑** | 可以（sim/render_backend 都选 cpu） | 重，依赖 RTX 生态，CPU 体验差 | 可以 | 可以但成熟度低 | 可以 | 可以 |
| **Windows 支持** | 有官方 wheel | Windows 支持弱、安装重 | 好 | 一般 | 好 | 好 |
| 机器人资产 | 内置 Panda 等主流臂，URDF/控制器齐全 | 资产迁移成本 | 需自己配 | 少 | 需自己配 | 就是 ManiSkill 的下层 |
| 控制器库 | PD 关节位姿/增量、EE delta pose、mimic 夹爪等开箱即用 | 全但复杂 | 要自己搭 | 要自己搭 | 简陋 | 需自己封装 |
| LLM-Agent 生态 | 已有 FAEA 等 LLM 直控验证 | RL 向为主 | RL 向为主 | 早期 | 早期 | 无 |
| 上手成本 | 低（gymnasium API） | 高 | 中 | 中高 | 低 | 高 |
| 许可 | Apache-2.0（可商用/可闭源部署） | NVIDIA 限制条款 | Apache-2.0 | Apache-2.0 | Zlib | Apache-2.0 |

### 1.2 选择理由

1. **硬件现实**：本机是 CPU torch + Windows。Isaac 系虽然效果最好，但绑定 NVIDIA GPU/驱动栈，安装体积和维护成本对一个 demo 过重；ManiSkill3 明确支持 `sim_backend="cpu", render_backend="cpu"`，在本机稳定运行。
2. **接触任务质量**：抓放任务成败全看接触/摩擦仿真，PhysX 在刚体接触上成熟可靠；实测闭合夹爪抓取、抬升不掉、入盒判定都符合物理直觉（MuJoCo 软接触在细二指夹爪上常需要大量调参）。
3. **Panda 开箱即用**：内置 panda_v2.urdf、多种控制器、`agent.tcp`、TableSceneBuilder、官方 motionplanning 示例（pick_cube 等），本项目的运动层几乎是照着官方示例的时序实现的，踩坑面最小。
4. **Agent 生态背书**：FAEA 范式已验证"LLM 直接 function-call 控制 ManiSkill3 环境"可行，技术风险有先例兜底。
5. **进可攻退可守**：将来若有显卡，同一份环境代码可切 GPU 后端并行跑上万 env 做数据/训练；要退回 CPU 也零成本。
6. **许可干净**：Apache-2.0，对"方便部署"友好。

### 1.3 放弃方案的核心原因

- **Isaac Sim/Lab**：CaP-X 等方案依赖它，但 RTX 依赖 + Windows 安装成本 + 本项目 CPU 约束直接否决；
- **MuJoCo/MJX**：许可和速度没问题，但二指夹爪接触需要更多建模调参，且没有现成 Panda 控制器/桌面场景，工期翻倍；
- **Genesis**：2025 年新框架，多引擎卖点在本项目用不到，资产/控制器生态尚薄，不适合作为可交付 demo 的底座；
- **PyBullet**：能跑但接触手感和维护状态（多年小更新）不适合抓放特写；
- **直接用 SAPIEN**：ManiSkill 本就是 SAPIEN 的上层，绕过它意味着自己重写 gym 封装、控制器、场景构建器，纯属重复造轮子。

## 2. 场景、组件与技能的设计选型

### 2.1 为什么自定义环境，而不是直接用 PickCube-v1

ManiSkill 自带 PickCube 是"单臂抓一个方块放进同一个盒子"，无法支撑"听懂指令、区分两个零件、二选一"的语义任务。因此自定义 `PickParts-v1`：

- **两个可区分物体**：A=蓝色圆柱、B=黄色方块。颜色+形状双特征是有意为之——当前阶段技能内部用真值位姿，下一阶段做 RGB-D 视觉时，蓝色/黄色 HSV 分割和圆/方形轮廓都是最鲁棒的识别特征；
- **一个固定空盒子**：任务目标单一、判定明确；
- 其余尽量复用官方积木（TableSceneBuilder、Panda、actors 构建器），把自定义代码压缩到 ~150 行。

### 2.2 组件选型思考

- **桌面/基座用 TableSceneBuilder**：它保证 Panda 基座位姿、初始关节角、桌面碰撞与官方示例一致，运动层参数（安全高度、可达范围）可以直接照搬官方经验；
- **盒子用 5 个 kinematic box（底板+四墙）而不是动态容器或纯可视化区域**：① kinematic 不会被机械臂碰跑，成功判定基准稳定；② 真有物理墙，夹爪下降越界时会被挡住，行为真实，也在调参阶段真实暴露了"零件 B 太靠盒墙导致指尖撞墙"的问题；③ 用 ActorBuilder 可精确控制壁厚/内腔，比用 URDF 轻量；
- **零件做成动态刚体**：必须真实响应夹爪接触和重力，"抓起/入盒"才有物理意义；
- **圆柱初始姿态绕 Y 轴 -90°**：SAPIEN/PhysX 圆柱几何体轴向沿本地 X，这是组件层面最反直觉的一点（详见技术文档 2.5 和执行记录）；
- **只保留两个相机位**：一个 128×128 腕外俯视（给未来感知）、一个 512×512 观察视角（human 渲染）。当前不做无用的多相机/点云配置，避免过度工程。

### 2.3 布局选型：可达性优先 + 安全裕量

- 所有坐标都先在 Panda 工作空间内粗选，再用逆解实测可达（`PandaMotion._ik` 暖启动收敛即通过）；
- 零件 A/B 左右分区（y 负/正），盒子固定远侧 y=0.25，三点不共线且距离适中，运动路径短；
- 零件 B 的 y 上限（0.08）不是随手定的：张开夹爪的指尖外沿到 TCP 约 0.05 m，盒墙近边在 y≈0.14，留 1 cm 裕量。**先用随机范围暴露问题，再用物理测量收窄边界**，而不是拍脑袋；
- 随机化只动 x/y（方块加竖直轴朝向），不随机倾斜——桌面抓放的初始接触条件保持可比，便于回归测试和将来策略学习。

### 2.4 控制模式：为什么是 pd_joint_pos（8 维绝对关节角）

ManiSkill 的 Panda 自带多种控制器，选择逻辑：

| 控制模式 | 评价 |
|---|---|
| `pd_joint_delta_pos` | 增量控制适合在线伺服/学习策略，但执行规划轨迹要不断积分，累积误差难调试 |
| `pd_ee_delta_pose` | 笛卡尔增量直观，但每步内部仍要做 IK，且旋转参数化（轴角）调试复杂 |
| **`pd_joint_pos`（选用）** | 直接给 7 关节绝对目标角 + 1 维夹爪，**与官方 motionplanning 示例的动作布局完全一致**；逆解输出可以原样下发，规划与执行语义一一对应，轨迹可复现、可逐帧核对 |

这也是运动规划类任务的事实标准：规划器输出关节轨迹，PD 位置控制器负责跟踪。

### 2.5 运动规划：mplib → pinocchio CLIK 自实现的取舍

- **首选本是 mplib**（ManiSkill 官方运动规划库，RRT-Connect + FCL 碰撞检测 + IK）。但官方只发布 Ubuntu（manylinux）wheel，nightly release 也无 Windows 版；PyPI 上的 `mplib 0.2.1` 是同名无关旧包；源码编译依赖 OMPL/FCL，在 Windows 上不现实。**结论：无法安装，放弃**；
- **替代方案**：SAPIEN 自带的 pinocchio wrapper（`robot.create_pinocchio_model()`）提供 CLIK 阻尼最小二乘逆解，conda-forge 一条命令装好，坐标系与仿真同源；
- **为什么不用 RRT 也够用**：本场景障碍极其规则（桌面 + 两个矮零件 + 一个矮盒），固定顶抓姿态 + "统一安全高度平移、只在目标正上方竖直升降"的路径模板天然无碰撞，把三维避障问题降维成一维高度选择，确定性 100%、零随机性、每次轨迹可复现——这比引入随机规划器更适合 demo 和回归测试；
- **轨迹平滑手段**：6 mm 笛卡尔点 + 逐点 IK 暖启动（关节解连续，避免奇异点翻腕）+ 0.06 rad 单步增量细分（速度受限，PD 跟得上）。

### 2.6 技能粒度：为什么是 move_to / pick / place 三个

- **原子性**：每个技能对应一个可独立验证的物理结果（到达/抓起/放好），返回值自带成功判据；
- **可组合**：`pick + place` 覆盖当前唯一任务，将来 `move_to + push + place` 可组合新任务；
- **LLM 友好**：粒度不能太细（如果暴露"关第 3 个关节"这种接口，LLM 无法正确使用）也不能太粗（只给一个 do_task 就失去规划意义）。物体级动作（pick 哪个、place 到哪）正好是语言模型语义理解的舒适区；
- **面向 MCP 化**：这三个无状态、入参简单、结果结构化的工具，天然适合中期包装成 MCP server——大脑可以整体换成任何框架/任何云端，身体侧技能不动。

## 3. Agent 框架与 LLM 选型

### 3.1 候选对比

| 维度 | **Qwen-Agent 0.0.34（当前选用）** | LangGraph 1.0（中期目标） | AutoGen | CrewAI |
|---|---|---|---|---|
| 定位 | 轻量 function-calling Agent SDK | 显式状态图编排框架 | 多 Agent 对话框架 | 角色化多 Agent 编排 |
| 上手成本 | 极低，Assistant+Tool 两个概念 | 中（StateGraph/Node/Edge/Checkpointer） | 中 | 低但黑盒 |
| 原生 function-calling | 是（OpenAI 兼容） | 是（透传模型工具协议） | 是 | 封装层较重 |
| 状态持久化/断点续跑 | 无内建 | **内建 checkpointer（SQLite 等）** | 弱 | 弱 |
| 轨迹可观测/评估 | 打印日志级 | LangSmith/流式状态，适合迭代优化 | 一般 | 一般 |
| 人在环路（审批/接管） | 要自己写 | 内建 interrupt | 一般 | 一般 |
| 项目维护状态 | 活跃 | 2025-10 GA，活跃 | **2025-10 起进入维护模式**，新项目不建议 | 活跃 |
| 与本项目匹配度 | 当前任务两步工具调用，完全够用 | 任务变复杂（重试/多步/感知）后收益大 | 杀鸡用牛刀且生态转向 | 控制粒度太粗，不适合精确动作 |

另外排除：**RoboOS 2.0**（面向多机器人长期任务的重型框架，引入成本远超 demo 需要）。

### 3.2 当前为什么选 Qwen-Agent

1. **任务形态匹配**：当前规划深度就是"1 次 pick + 1 次 place"，Qwen-Agent 的 Assistant + BaseTool 用 ~50 行代码就能跑通完整闭环，没有多余抽象；
2. **协议兼容直接**：`model_type="oai"` 原生吃 OpenAI 兼容接口，DeepSeek/Qwen 等可一键切换；
3. **工具定义简单**：BaseTool 的 name/description/parameters 与 OpenAI function-calling 一一对应，加技能就是加类；
4. **替换成本低**：技能层（sim_skills）不依赖 Qwen-Agent 的私有能力，只是 BaseTool 基类薄封装，迁移 LangGraph 时把三个工具包一层即可。

### 3.3 中期迁移 LangGraph 1.0 的触发条件与理由

当出现以下任一需求时迁移（已在项目路线中确认）：

- 需要失败重试/反思分支（pick 没抓起→换角度再来）、需要显式状态机（感知→规划→执行→校验）；
- 需要轨迹留存与回放做优化、需要人在关键步骤审批接管；
- 技能 MCP 化后大脑多实例部署。

LangGraph 的 checkpoint、状态流式输出、interrupt 正好对应这三类需求；AutoGen 因进入维护模式被排除，CrewAI 控制粒度不够。

### 3.4 LLM：为什么用 DeepSeek（OpenAI 兼容）

- 中文指令理解和工具调用稳定性满足任务（实测严格按 pick→place 两步调用，不添加冗余动作）；
- OpenAI 兼容协议，切换成本仅为改 `.env` 三个变量；
- 云端 API 不占本机算力，符合"CPU 机器跑仿真、云侧做大脑"的部署分工；
- 成本低，迭代调试可接受。

### 3.5 小脑远期：为什么 VLA 唯一候选是 SmolVLA 450M

若将来要从"确定性运动规划"升级到"端到端视觉-语言-动作策略"，硬件约束（4GB 显存/CPU 可推理）下：

| 方案 | 结论 |
|---|---|
| **SmolVLA 450M（LeRobot，Apache-2.0）** | **唯一现实候选**：450M 参数量 CPU 可推理，社区有消费级显卡微调路径（LoRA 全参微调约需 24GB 显存，可借助云训练），许可宽松 |
| OpenVLA 7B | 7B 量级本机推理都困难，微调门槛更高 |
| π0 / RT-2 | 权重/数据开放度低、硬件门槛高，排除 |

确定性规划（当前）与 VLA（远期）共享同一个 `panda_motion` 式接口边界，切换小脑不动大脑。

## 4. 总体选型结论（一页速览）

| 层 | 选型 | 关键理由 | 升级路线 |
|---|---|---|---|
| 身体（仿真器） | ManiSkill 3.0.1 + SAPIEN/PhysX | CPU/Windows 可跑、接触真实、Panda 与控制器开箱即用、FAEA 背书、Apache-2.0 | 有显卡后切 GPU 后端；接真机替换 env 适配层 |
| 机器人 | 内置 Panda（pd_joint_pos，8 维） | 官方 motionplanning 同款，轨迹可复现 | 真机 SDK 同接口替换 |
| 小脑（运动） | pinocchio CLIK + 笛卡尔直线 + 安全高度模板（自研） | mplib 无 Windows 版；规则场景无需 RRT，确定性 100% | 远期 SmolVLA 450M |
| 技能层 | pick / place / move_to（Qwen-Agent BaseTool） | 物体级语义粒度，LLM 舒适区，无状态易迁移 | **MCP server 化** |
| 大脑框架 | Qwen-Agent 0.0.34 | 两步任务最简闭环，迁移成本低 | **LangGraph 1.0**（重试/状态/人在环路） |
| LLM | DeepSeek（OpenAI 兼容云端 API） | 中文+工具调用稳定、零本地算力、可一键换模型 | 任意 OpenAI 兼容模型 |
| 感知 | 暂用仿真真值，视觉为下一阶段 | RGB-D 颜色/形状分割特征已在场景设计中预留 | faster-whisper 语音、edge-tts、RGB-D 分割 |
