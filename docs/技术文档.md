# PickParts XLeRobot 技术文档

> 本文对应 2026-09-21 的当前代码。运行主链路位于
> `src/pickparts_agent/`，默认 Web 地址为 `http://127.0.0.1:8765`。

## 1. 系统概览

PickParts 在 ManiSkill 3 / SAPIEN 中构建 XLeRobot v0.3 轮式双臂机器人和
桌面操作场景。当前 PoC 锁定底盘和左臂，由右臂执行以下任务：

- 定位场景目录中的任意物块或盒子；
- 抓取物块并放入任意盒子；
- 将一个物块放到另一个物块上；
- 随机重置全部物体，保证物体位于桌面、互不重叠且机械臂可达；
- 在运行中随机添加物块或盒子；
- 动作失败后通过 ReAct 执行 retry、replace、replan、ask_user 或 abort。

系统采用“语义规划、视觉接地、物理执行、视觉复核”的闭环。LLM 只产生对象
ID、关系和原子动作，不产生坐标或关节角。物体三维位置由 RGB-D 观测在原子
运行时计算。

### 1.1 非特权观测边界

Agent 和原子操作只能使用：

- 工作区相机 RGB；
- 米制深度；
- 相机内参与 `camera_to_base` 标定；
- 机器人关节位置 `qpos` 和速度 `qvel`；
- 不包含位置真值的物体语义目录 `id/kind/label/color`。

场景生成器必须使用 actor pose 创建物理对象，但 pose 只留在私有构造层。
`Simulation.object_specs` 对外只返回语义元数据，`Frame` 只包含传感器和本体
状态。[`Simulation.object_specs`](../src/pickparts_agent/scene/simulation.py#L89-L92)
和 [`Frame`](../src/pickparts_agent/scene/perception.py#L8-L15) 是这条边界的主要接口。

`PickPartsEnv._get_obs_extra()` 和 `evaluate()` 均返回空字典，避免奖励、成功
标志或物体真值进入上层：
[`scene/simulation.py:L70-L74`](../src/pickparts_agent/scene/simulation.py#L70-L74)。

## 3. 场景设计

### 3.1 场景分层

场景由两层组成：

1. `_SceneObjects` 管理物体语义目录、私有初始位置、actor 和随机采样；
2. `PickPartsEnv` 管理机器人、桌面、地面、相机和 ManiSkill 环境参数。

这样拆分后，场景构造可以读取 actor pose 来避免新物体与现有物体重叠，但感知
和 Agent 无法访问 `_placements` 或 `_actors`。对外只暴露
`Simulation.object_specs` 的元数据副本。

对应代码：

- 对象构造层：[`scene/objects.py:L74-L195`](../src/pickparts_agent/scene/objects.py#L74-L195)
- ManiSkill 环境：[`scene/simulation.py:L18-L74`](../src/pickparts_agent/scene/simulation.py#L18-L74)
- 窄仿真接口：[`scene/simulation.py:L77-L168`](../src/pickparts_agent/scene/simulation.py#L77-L168)

### 3.2 机器人、桌面和相机

`PickPartsEnv` 使用以下配置：

```text
robot_uids="pickparts_xlerobot"
obs_mode="rgbd"
control_mode="pd_joint_pos"
reward_mode="none"
sim_backend="cpu"
render_backend="cpu"
```

场景几何：

| 对象 | 类型 | 几何 |
|---|---|---|
| 桌面 | 静态 box | half-size `(0.30, 0.22, 0.025)`，中心 `(0, -0.45, 0.695)` |
| 桌腿 | 4 个静态 box | half-size `(0.015, 0.015, 0.335)` |
| 地面 | 静态 box | half-size `(2, 2, 0.02)` |
| 物块 | 动态 box | half-size `(0.012, 0.012, 0.018)` |
| 盒子 | 静态复合体 | 底板和四面真实碰撞墙 |

桌面和地面位于
[`PickPartsEnv._load_scene`](../src/pickparts_agent/scene/simulation.py#L40-L60)，
物块和盒子位于
[`_SceneObjects._build_actor`](../src/pickparts_agent/scene/objects.py#L146-L166)。

工作区相机 `workspace` 为 640x480，位置约 `(0.45, -0.90, 1.25)`，看向
`(0, -0.25, 0.75)`。配置见
[`_default_sensor_configs`](../src/pickparts_agent/scene/simulation.py#L27-L30)。
`Simulation.observe()` 将毫米深度转换为米，并返回 `Frame`：

```python
Frame(
    rgb,
    depth,
    intrinsic,
    camera_to_base,
    qpos,
    qvel,
)
```

实现位置：
[`Simulation.observe`](../src/pickparts_agent/scene/simulation.py#L151-L165)。

### 3.3 动态物体目录

对象元数据格式固定为：

```json
{
  "id": "block_1",
  "kind": "block",
  "label": "物块 1",
  "color": [0.81, 0.068, 0.85]
}
```

字段含义：

- `id`：Planner、原子和 UI 使用的稳定语义引用；
- `kind`：当前只支持 `block` 和 `box`；
- `label`：用于用户同义描述匹配；
- `color`：本地视觉身份，不包含位置。

默认目录包含 `A`、`B` 和 `box`，最多允许 6 个对象。新增对象自动生成
`block_N` 或 `box_N`，并从色环中选择与现有颜色差异最大的高饱和颜色。
目录和颜色校验位于
[`validate_specs`](../src/pickparts_agent/scene/objects.py#L24-L51)，
新增逻辑位于
[`_SceneObjects.add`](../src/pickparts_agent/scene/objects.py#L168-L195)。

### 3.4 随机可达布局

重置或创建场景时，不使用固定 A/B/盒子坐标，而是执行有界随机采样：

1. 在完整桌面范围按 25 mm 网格生成候选 XY；
2. 对每个候选点，在抓取、抬升、悬停和双层叠放高度上调用真实 URDF IK；
3. 只缓存全部高度均可达的网格；
4. 随机打乱候选点，加入小范围随机扰动；
5. 粗网格没有可用位置时，再使用 5 mm 子网格补充搜索；
6. 校验物体完整 footprint 位于桌面边界内；
7. 校验对象之间的安全间距和物块的夹爪操作空间；
8. 稀疏默认场景优先预留一个可添加盒子的位置；
9. 在有界重试内找不到布局时，明确返回容量错误。

可达性筛选见
[`_reachable`](../src/pickparts_agent/scene/objects.py#L54-L61) 和
[`_reachable_cells`](../src/pickparts_agent/scene/objects.py#L64-L71)；
随机候选与约束见
[`_candidate_xy`](../src/pickparts_agent/scene/objects.py#L106-L119) 和
[`_sample`](../src/pickparts_agent/scene/objects.py#L121-L139)。

这些约束保证的是当前 XLeRobot 右臂、当前桌面和当前原子动作的可达性，不表示
任何机器人或任意形状物体都可操作。

### 3.5 添加物体与重置

Web 添加对象：

```text

{"kind": "block"}
```

或：

```text

```

处理链路：

```text
FastAPI /api/objects
  -> Console 工作队列
  -> RobotBackend.add_object
  -> Simulation.add_object
  -> _SceneObjects.add
  -> 更新 WorldState.catalog
  -> 旧视觉记录标记为不可见
  -> 重建 VisualLocator
```

对应位置：

- API：[`web.py:L301-L309`](../src/pickparts_agent/interfaces/web.py#L301-L309)
- 后端刷新：[`RobotBackend.add_object`](../src/pickparts_agent/interfaces/web.py#L78-L86)
- 物理创建：[`Simulation.add_object`](../src/pickparts_agent/scene/simulation.py#L94-L98)

重置场景时保留当前对象目录，但关闭并重建 `Simulation`，因此所有对象获得新的
随机可达位置；同时重新创建 `WorldState`、清空会话历史和刷新定位器：
[`RobotBackend.reset`](../src/pickparts_agent/interfaces/web.py#L59-L76)。

### 3.6 视觉定位

`VisualLocator` 根据目标是否在实时目录中选择感知路径：

```text
目录内 ID
  -> ScenePerception
  -> 全图 HSV 身份分割
  -> 连通域、深度覆盖和深度连通性校验
  -> RGB-D 反投影

开放文本描述
  -> CloudPerception
  -> VLM 仅返回 RGB 图中的 bbox
  -> 本地校验 bbox、深度覆盖和深度连通性
  -> RGB-D 反投影
```

路由代码：
[`VisualLocator.locate`](../src/pickparts_agent/services/cloud.py#L224-L228)。

目录对象优先使用本地 `ScenePerception`，因为颜色由场景生成器主动分配，身份
确定且无需云端猜测。该模块会拒绝：

- 目标不可见或贴近图像边缘；
- 可见像素过少；
- 有效深度覆盖不足；
- 同色目标存在多个显著连通域；
- bbox 内存在不一致的深度表面；
- 物块只露出不足以定位抓取中心的窄条。

几何输出包含 `bbox`、`point`、`top_z`、`bottom_z`、`extent` 和
`confidence`，由
[`ScenePerception.locate`](../src/pickparts_agent/scene/perception.py#L118-L219)
计算。反投影公式实现在
[`backproject`](../src/pickparts_agent/scene/perception.py#L18-L32)。

开放描述走 `CloudPerception`。VLM 不接收深度或三维坐标，只返回原图像素 bbox；
本地代码要求 `0 <= x1 < x2 <= width`、`0 <= y1 < y2 <= height`，再使用
真实深度完成三维接地：
[`CloudPerception.locate`](../src/pickparts_agent/services/cloud.py#L102-L212)。

## 4. 原子操作设计

### 4.1 原子契约

每个原子都继承 `Atom`，声明：

- `name`：供 Planner 和 Reactor 引用；
- `description`：写入模型能力目录；
- `parameters`：参数 schema；
- `check_pre()`：执行前检查；
- `run()`：运行时视觉接地和物理动作；
- `verify()`：执行后验证。

统一入口 `Atom.call()` 固定执行：

```text
check_pre
  -> 失败：AtomResult(error_kind="precondition")
run
  -> 失败：直接返回动作错误
verify
  -> 失败：AtomResult(error_kind="verify")
成功：返回 AtomResult(success=True)
```

数据结构和调用逻辑位于
[`agent/atoms/base.py:L6-L54`](../src/pickparts_agent/agent/atoms/base.py#L6-L54)。
`AtomContext` 向原子注入 `sim`、`locate`、`kin`、`state` 和事件回调，但不
注入 actor 或场景真值。

### 4.2 注册和参数校验

默认注册表包含 11 个原子：
[`build_default_registry`](../src/pickparts_agent/agent/atoms/__init__.py#L10-L14)。

`AtomRegistry.validate_call()` 在计划执行前检查：

- 调用对象只能包含 `atom` 和 `args`；
- 原子名称必须已注册；
- 参数必须满足 required、类型、有限数值、范围和枚举约束；
- 字符串对象引用不能为空，且最长 160 字符。
- `table` 是虚拟支撑面，不能作为普通对象传给定位、抓取或对象放置原子。

实现位置：
[`agent/atoms/registry.py:L22-L56`](../src/pickparts_agent/agent/atoms/registry.py#L22-L56)。
`catalog_for_prompt()` 从同一注册表生成 Planner/Reactor 的能力目录，避免
提示词和可执行实现维护两套原子清单。

| `place_on` | `target` | 根据支撑顶面和抓取偏移，把持物放到物块上 | [`PlaceOn`](../src/pickparts_agent/agent/atoms/placement.py#L147-L186) |
| `place_on_table` | 无 | 实测桌面、选择安全可达空位并释放持物 | [`PlaceOnTable`](../src/pickparts_agent/agent/atoms/placement.py#L9-L78) |
| `reset_arm` | 无 | 空手时回到右臂 rest 姿态 | [`ResetArm`](../src/pickparts_agent/agent/atoms/placement.py#L125-L144) |

虽然 `carry_to` 的参数名仍是 `container`，它可以指向物块或盒子。最终放置原子
由目的对象类型决定：

- `kind=box`：使用 `release_into`，关系为 `in`；
- `kind=block`：使用 `place_on`，关系为 `on`。
- `table`：使用 `place_on_table`，由原子在运行时测量支撑面并选择落点。

### 4.4 运行时坐标接地

LLM 计划只包含：

```json
{"atom": "carry_to", "args": {"container": "B"}}
```

不包含：

```json
{"x": -0.08, "y": -0.34, "z": 0.84}
```

坐标接地发生在原子内部：

1. `find_object` 从 `locate(frame, target)` 获得视觉几何；
2. `WorldState.apply_observation()` 保存当前 frame 的测量；
3. 运动原子读取 `ObjectRecord.point/top_z/bottom_z/extent`；
4. `_cartesian()` 调用 URDF IK；
5. `Simulation.move_right()` 执行 PD 关节位置控制；
6. 原子重新读取 qpos 或 RGB-D 验证结果。

运动辅助函数见
[`_cartesian`](../src/pickparts_agent/agent/atoms/manipulation.py#L33-L61)。
它对大位移生成约 8 mm 的笛卡尔路点，每个路点重新求 IK；若 TCP 有小幅静态
跟踪偏差，会先等待并执行一次有限本体补偿，最终仍要求 TCP 误差不超过 8 mm。

IK 只解析机器人 URDF，不读取场景对象：
[`ArmKinematics`](../src/pickparts_agent/scene/kinematics.py#L12-L78)。

### 4.5 抓取和持物状态

`grasp` 只确认夹爪闭合，不立即宣告抓取成功。`lift` 抬升后必须重新定位同一
物体，视觉高度增量至少为 3.5 cm 才设置 `held_object`。

成功抬升后还记录：

- `grasp_offset`：TCP 与物体视觉中心的偏差；
- `grasp_bottom_offset`：TCP 与物体底面的高度差。

`carry_to`、`release_into`、`place_on` 和 `place_on_table` 使用这些观测偏差补偿放置位置。张开
夹爪会清除 held/grasp 状态并使旧位置记录失效，防止“幽灵持物”：
[`WorldState.set_gripper`](../src/pickparts_agent/agent/state.py#L58-L69)。

### 4.6 放入盒子、叠放和桌面校验

`verify_state` 不根据单个中心点猜测关系，也不把“看不见”当作成功。
校验前等待物体落定并读取新帧；第一次视野不完整时，可先将空机械臂复位以清除
遮挡，再采集一次。第二次仍不可见则返回 `lost_object`。

三类关系：

- `table`：从目标附近 RGB-D 点云测量宽广水平桌面，要求物体底面与桌面高度
  误差小于 4 mm；
- `on`：要求源和支撑物水平中心接近、垂直关系合理，且源底面接近支撑顶面；
- `in`：要求源物体完整观测 footprint 位于盒子内沿内，而不仅是中心点在盒内，
  并要求源底面低于盒沿。

`place_on_table` 不调用 `find_object(table)` 或 VLM。它从实时 RGB-D 点云选择
机器人工作台高度带内、目标附近占主导的宽水平面，并只使用同一连通支撑区域。
随后按持物 footprint 和安全间距过滤桌边、物块、盒子及机器人遮挡，再以完整
笛卡尔路点进行连续 IK 筛选。最终校验还要求物体 footprint 位于实测桌面凸包内。
没有可见支撑面、安全空位或可达路径时失败闭合，由 ReAct 决定恢复方式。

校验逻辑见
[`VerifyState.run`](../src/pickparts_agent/agent/atoms/perception.py#L57-L108)，
桌面测量见
[`table_height`](../src/pickparts_agent/scene/perception.py#L35-L79)。

### 4.7 三条标准动作链

把 A 放进 box：

```text
find_object(A)
find_object(box)
reach_above(A)
grasp(A)
lift()
carry_to(box)
release_into(box)
verify_state(A, box, in)
reset_arm()
```

把 A 放到 B 上：

```text
find_object(A)
find_object(B)
reach_above(A)
grasp(A)
lift()
carry_to(B)
place_on(B)
verify_state(A, B, on)
reset_arm()
```

把 A 放到桌面：

```text
find_object(A)
reach_above(A)
grasp(A)
lift()
place_on_table()
verify_state(A, table, table)
reset_arm()
```

Planner 可以根据当前持物状态重规划剩余步骤，但计划始终是扁平 AtomCall
列表，不允许循环容器或嵌套计划。

## 5. Agent 设计

### 5.1 分层架构

当前主链路没有把 Qwen-Agent 作为编排核心，而是在 OpenAI 兼容接口上实现轻量
具身 Agent。

| 层 | 主要职责 | 代码位置 |
|---|---|---|
| WorldState | 保存目录、视觉观测、夹爪和持物状态 | [`agent/state.py`](../src/pickparts_agent/agent/state.py) |
| Planner | 可行性评估，生成扁平原子计划 | [`Planner`](../src/pickparts_agent/agent/planner.py#L50-L170) |
| ReActExecutor | 顺序执行、预算、事件、恢复应用和最终复核 | [`ReActExecutor`](../src/pickparts_agent/agent/executor.py#L18-L152) |
| Reactor | 失败后选择恢复策略 | [`Reactor`](../src/pickparts_agent/agent/reactor.py#L54-L98) |
| Orchestrator | 组装各层，管理一次用户回合 | [`Orchestrator`](../src/pickparts_agent/agent/orchestrator.py#L21-L44) |
| JSONChat | 严格 JSON 模型边界和 Think 配置 | [`JSONChat`](../src/pickparts_agent/agent/llm.py#L36-L94) |

`Endpoint.qwen_config()` 仍保留 Qwen-Agent OpenAI 消息兼容工具，但当前
`build_orchestrator()` 主链路直接使用 `JSONChat`。

### 5.2 WorldState

`WorldState` 是线程安全的非特权黑板，包含：

```text
catalog           对象语义目录，不包含位置
objects           最新视觉 ObjectRecord
frame_id          当前观测序号
gripper_open      夹爪状态
held_object       已经视觉确认被持有的对象
grasp_target      最近闭爪目标
grasp_offset      TCP 与物体中心偏差
grasp_bottom_offset
```

`ObjectRecord` 保存 bbox、三维点、置信度、frame_id、可见性以及视觉测得的
顶部、底部和 extent：
[`ObjectRecord`](../src/pickparts_agent/agent/state.py#L8-L27)。

关键原则：

- `catalog` 是语义事实，不是位置事实；
- 定位失败会把旧记录标为 `visible=False`；
- 除当前持物可标记为 `gripper` 外，不从中心点自动推断 table/box；
- `on/in/table` 必须由 `verify_state` 的新鲜几何观测建立。

对应实现：
[`WorldState.apply_observation`](../src/pickparts_agent/agent/state.py#L95-L106) 和
[`_infer_placement`](../src/pickparts_agent/agent/state.py#L88-L93)。

### 5.3 Planner

`Planner.analyze()` 接收：

```json
{
  "goal": "把 A 放到 B 上面",
  "world": {
    "catalog": {},
    "objects": {},
    "held_object": null
  }
}
```

模型输出严格 JSON：

```json
{
  "feasible": true,
  "blockers": [],
  "steps": [
    {"atom": "find_object", "args": {"target": "A"}}
  ],
  "rationale": "面向用户的简短任务理解"
}
```

Planner 执行两级校验：

1. `AtomRegistry.validate_call()` 检查每个原子及参数；
2. `_validate_sequence()` 检查语义顺序。

顺序校验包括：

- 源和目的都必须先定位；
- 抓取前必须 reach，且夹爪为空；
- 搬运前必须成功 lift；
- 不能把物体放到自身；
- 放置动作必须紧跟匹配源/目的的 `verify_state`；
- box 使用 `release_into`，block 使用 `place_on`；
- 桌面关系和 `at="table"` 必须一致；
- 计划结束时不能留下未验证的放置。

系统提示词位于
[`agent/planner.py:L6-L39`](../src/pickparts_agent/agent/planner.py#L6-L39)，
结构和顺序校验位于
[`Planner.analyze`](../src/pickparts_agent/agent/planner.py#L55-L89) 和
[`_validate_sequence`](../src/pickparts_agent/agent/planner.py#L91-L170)。

### 5.4 ReActExecutor

`ReActExecutor.execute()` 是物理执行主循环：

1. 复制计划并保存原始 `verify_state` 目标；
2. 建立 `AtomContext`；
3. 逐个调用 `registry.get(atom).call()`；
4. 向 Web/CLI 输出 plan、step、activity 和 react 事件；
5. 成功时推进指针；
6. 失败时调用 Reactor；
7. 应用恢复决策并继续执行；
8. 全部步骤完成后，再次执行原始目标的 `verify_state`；
9. 只有最终复核成功才返回 `success=True`。

原始目标独立于可变计划保存，因此 Reactor 不能通过 `replace` 删除失败的
`verify_state` 来伪造成功。实现见
[`agent/executor.py:L44-L117`](../src/pickparts_agent/agent/executor.py#L44-L117)。

预算：

| 预算 | 上限 |
|---|---:|
| `MAX_REACT_ITERS` | 4 |
| `MAX_ATOM_CALLS` | 25 |
| `MAX_LLM_CALLS` | 8 |

预算常量位于
[`agent/executor.py:L6-L8`](../src/pickparts_agent/agent/executor.py#L6-L8)。
`fatal` 不进入模型反思，立即中止并设置 `recovery_required=True`。

### 5.5 Reactor

Reactor 接收失败原子、错误类型、观测、剩余计划和 WorldState 快照，并输出：

| 决策 | 含义 |
|---|---|
| `retry` | 先插入准备步骤，再重试当前失败原子 |
| `replace` | 用非空原子列表替换当前失败原子 |
| `replan` | 重新调用 Planner 生成剩余计划 |
| `ask_user` | 需要人工澄清或确认 |
| `abort` | 安全中止 |

约束：

- `replace` 不能为空，防止直接跳过失败动作；
- `replan/ask_user/abort` 不能携带 steps；
- 所有新步骤仍经 `AtomRegistry` 校验；
- `fatal` 必须直接 abort；
- Reactor 不可用时，fatal 回退 abort，其他错误回退 replan。

提示词和约束见
[`agent/reactor.py:L8-L42`](../src/pickparts_agent/agent/reactor.py#L8-L42) 和
[`Reactor.decide`](../src/pickparts_agent/agent/reactor.py#L63-L98)。

### 5.6 Orchestrator 与模型 Think

`Orchestrator.turn()` 完成一次用户回合：

```text
发布“理解指令”摘要
  -> Planner.analyze
  -> 发布公开 plan rationale
  -> 不可行：返回 blockers
  -> 可行：ReActExecutor.execute
  -> 成功：追加“还需要我做什么？”
  -> 写入多轮 history
```

代码位置：
[`Orchestrator.turn`](../src/pickparts_agent/agent/orchestrator.py#L32-L44)。

`build_orchestrator()` 创建统一 WorldState、注册表、Planner、Reactor、
ReActExecutor 和 JSONChat：
[`agent/orchestrator.py:L47-L60`](../src/pickparts_agent/agent/orchestrator.py#L47-L60)。

Think 只在官方 DeepSeek HTTPS 端点和明确支持的模型名上启用：
[`supports_thinking`](../src/pickparts_agent/agent/llm.py#L13-L29)。
模型可以在服务端使用 Think 能力，但应用不读取、不存储、不展示
`reasoning_content`。Web 只展示：

- 用户要求摘要；
- 面向用户的计划 rationale；
- 当前原子及参数；
- 观测结果；
- 恢复决策和原因。

这与内部思维链不同。边界位于
[`JSONChat._complete`](../src/pickparts_agent/agent/llm.py#L49-L65)。

### 5.7 完整数据流

```text
用户文字/ASR
  -> Orchestrator.turn
  -> Planner.analyze(goal, WorldState.snapshot)
  -> AtomRegistry 校验
  -> Planner 语义顺序校验
  -> ReActExecutor.execute
       -> Atom.call
            -> check_pre
            -> Simulation.observe
            -> VisualLocator
                 -> ScenePerception（目录对象）
                 -> CloudPerception（开放描述）
            -> WorldState.apply_observation
            -> ArmKinematics.solve
            -> Simulation.move_right
            -> verify
       -> 失败：Reactor.decide
       -> retry / replace / replan / ask_user / abort
  -> 原始目标最终视觉复核
  -> success / failure
```

## 6. 安全与错误处理

### 6.1 必须保持的边界

1. LLM 只能输出语义对象引用和原子调用，不能输出坐标、关节角或底层动作。
2. 计划必须是顶层扁平 AtomCall 列表，禁止嵌套循环。
3. 感知只接收 `Frame` 和对象元数据，不能接收 env、actor 或 pose。
4. `catalog` 不是位置真值，位置必须来自新鲜 RGB-D 观测。
5. 看不见表示未知，不能沿用旧 placement 宣告成功。
6. 物理失败不能被模型文本覆盖。
7. `fatal` 必须立即停止，不允许模型重试。
8. 每个放置目标必须经过 `verify_state`，执行结束后还要再次复核原始目标。

### 6.2 错误类型

| `error_kind` | 含义 |
|---|---|
| `precondition` | 原子前置条件不满足 |
| `lost_object` | 目标不可见、遮挡或定位不确定 |
| `grip_failed` | 抬升后视觉未确认物体高度变化 |
| `unreachable` | IK 或运动目标不可达 |
| `verify` | 原子后置状态或 TCP 跟踪未通过 |
| `fatal` | 关节跟踪等物理安全错误 |

低层 `ValueError` 映射为 `unreachable`，`RuntimeError` 映射为 `fatal`：
[`_guard`](../src/pickparts_agent/agent/atoms/manipulation.py#L11-L21)。

调用展开、关联日志/产物、跨午夜记录、切换与重置后状态。

真实物理闭环覆盖：

- A 放到 B 上；
- B 放到 A 上；
- 默认物块放入默认盒子；
- 新增物块放入新增盒子；
- 多个随机 seed 的抓取、抬升、释放和视觉复核；
- TiPToP 对照系统在 seed 0 `A→B`、seed 3 `B→A`、seed 7 `A→box` 的开环端到端验收。

当前边界：

- 对象总数上限为 6，且实际容量受桌面可达空间影响；
- 新增物体类型当前只有 `block` 和 `box`；
- 开放文本可以通过 VLM 定位，但物理抓取仍受物体尺寸、形状、遮挡和夹爪能力约束；
- 当前只使用右臂，未实现底盘导航和双臂协同；
- 盒子是静态容器，不作为抓取目标；
- 未验证 XLeRobot 实机控制和仿真到现实迁移；
- ASR 文件接口已实现，麦克风硬件链路不属于当前主要验收范围。

## 10. TiPToP Mac/CPU 对照系统

`src/tiptop_mac/` 是独立对照包，用于在**同场景、同任务、同种子**下比较
TiPToP 风格开环 TAMP 与主系统 ReAct 闭环。该包不修改 `pickparts_agent` 的任何行为，
只复用其低层仿真、RGB-D、SciPy IK 与运动安全后端。

### 10.1 模块结构

```text
src/tiptop_mac/
  types.py        # Grasp/ObjectNode/TableSurface/SceneGraph/Predicate/MotionStep/TAMPPlan
  perception.py   # 一次性 RGB-D：HSV 分割、点云、RANSAC 桌面、顶部 4-DoF 抓取
  grounding.py    # 语言接地：on/holding 目标谓词（替代 Gemini）
  tamp.py         # CPU TAMP-lite：符号 BFS + IK/几何预检，生成完整轨迹
  executor.py     # OpenLoopExecutor：开环执行，失败即中止
  evaluation.py   # 外部裁判 judge_outcome：执行后新 RGB-D 判定，结果不回传控制器
  benchmark.py    # 双架构对比，输出 results.json / report.md
  cli.py          # python -m tiptop_mac.cli {run,benchmark}
  agent.py        # TiPToPAgent 组装与 build_tiptop_agent 工厂
```

### 10.2 与官方 TiPToP 的映射

| 官方模块 | Mac/CPU 适配 |
| --- | --- |
| FoundationStereo | ManiSkill metric depth |
| Gemini 检测/谓词 | LLM Grounding（on/holding） |
| SAM2 分割 | 目录 HSV 颜色分割 |
| M2T2 抓取 | block 顶部 4-DoF 抓取启发式（box 不生成抓取） |
| RANSAC 凸包 | RANSAC 水平面 + 边界框 |
| cuTAMP | CPU TAMP-lite（符号 BFS，500 状态上限） |
| cuRobo | SciPy IK + 笛卡尔 8mm 插值 + 跟踪校验 |
| 开环执行 | 轨迹预先确定；任一运动失败 abort，不 retry/replan |

### 10.3 谓词与规划语义

- 入盒与叠放统一为 `on(x,y)`，放置模式由支撑体几何类型推导（box → release into；
  block → place on surface；table → place on table），另支持 `holding(x)`。
- 初始支撑关系由实测几何推导：block 底部落在桌面 band 内为 `on(table)`；
  落在另一对象顶部区域为 `on(对象)`。
- 算子仅有 `pick(block)` 与 `place(block,support)`；支撑体不能是对象自身或其当前承载的
  后代对象；所有运动点在执行前完成 IK 预检与 footprint/碰撞校验。

### 10.4 抓取标定（与纯开环的偏离）

实测发现夹爪闭合时会把物体物理拖动约 1cm（方向随位姿变化），纯按 TCP 中心预排的
放置点会使 24mm 小物块失稳滚落。因此 `tamp.py` 在每次 lift 后插入一个固定的
`calibrate` 步骤：执行器用**本地 RGB-D** 量一次物体相对 TCP 的偏移（含底部高度），
把后续预定 waypoint 整体平移。该步骤：

- 对应官方 cuTAMP 的 grasp-relative 规划（放置目标相对抓取位姿计算）；
- 是流水线中无条件、固定的阶段，不读取任务结果，不产生 retry/replace/replan 分支；
- 标定测量本身失败按致命错误 abort，与 IK 预检失败同类。

### 10.5 外部裁判与对比方式

执行结束后由独立的 `judge_outcome` 用**新一帧 RGB-D** 判定：叠放要求两物块中心
XY 近重合（≤34mm）、中心高度差在一个物块高度 band（20–60mm）、且底部已落在支撑体上；
入盒要求 footprint 位于盒内且高度不越墙。裁判结果只用于报告，不反馈给控制器。

固定对比用例：seed 0 `A→B (on)`、seed 3 `B→A (on)`、seed 7 `A→box (in)`，
每个 case 各自新建全新 `Simulation`。benchmark 缺少云端配置时显式标记 skipped。

### 10.6 网页三 Agent

`RobotBackend.select_agent` 在唯一仿真工作线程构建目标引擎。构建成功后释放旧引擎的
LLM 客户端，三个引擎共用当前 Simulation；切换不改变物体位置。重新进入自研引擎时
创建新的 WorldState，避免复用 TiPToP 移动物体之前的旧观测。随机重置和动态添加物体
会同步刷新当前引擎的仿真引用与定位器。

`Console` 的 `switching` 状态与 busy/resetting/adding 一样禁止追加控制操作。
发生运动中止、需要恢复时，必须先重置。切换构建失败保留原引擎，页面给出可重试提示。

TiPToP 的 `on_stage` 用于显示理解、感知、规划、执行阶段；`on_event` 使用与自研引擎
相同的 plan/step/activity/finish 协议，逐项展示预生成的移动、夹爪、标定与复位动作。
结果中的 `verification: "open_loop"` 让前端明确显示开环完成，外部裁判仍只用于 benchmark。

## 11. 持久化日志与 Trace

`observability/recorder.py` 将一次 command/reset/add/switch 记录为一个 Run，
包含根 Span、子 Span、日志和产物。`run_start` 记录任务、指令、Agent、时间和 run_id；
`run_end` 记录结果、总耗时、原子动作/LLM/纠偏计数。失败或未完成任务的根 Span
保留真实状态；最终事件落盘后 Console 才恢复 ready。

TiPToP 单独追踪语言接地、场景感知、全局 TAMP 和逐个开环动作；自研 Agent 保留
Planner/Executor/ReAct/Atom 层级。UI 活动摘要和步骤变化同步进入关联 Span 的日志。
RGB-D、状态和 LLM 输入输出存放在 `logs/artifacts/<run_id>/`；JSONL 日志自动脱敏，
异常堆栈仅保存在本地文件，HTTP 日志详情仅提供异常类型。

控制台当前运行链接指向 `/history?run=<run_id>`。历史页支持日期、Agent、状态和
文本筛选，运行详情实时刷新。Span 瀑布图按时间对齐并呈现父子层级，可展开查看属性；
日志支持级别、文本与 Span 关联筛选，产物直接链接到对应运行。
前端将动态文字作为文本呈现，异步请求通过版本检查避免旧响应覆盖新选择。

默认保留 7 天；通过 `.env` 中的 `PICKPARTS_LOG_DIR`、
`PICKPARTS_LOG_RETENTION_DAYS`、`PICKPARTS_LOG_LEVEL` 配置存储和日志级别。
